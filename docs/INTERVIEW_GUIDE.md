# 中高级大模型应用开发工程师面试要点

最后更新：2026-11-12

> 维护说明：本文件是面试要点的唯一维护位置，在线文档仅为早期副本，不再更新。新增考点时，同时在 `docs/DEVELOPMENT_GUIDE.md` 的对应关系表中补一行本项目的对应点。

## 面试框架

中级和高级的区别不在"会不会调模型"，而在能否把模型做成可靠、可评估、可控成本的产品：中级看做过且知道坑，高级看能设计、能取舍、能用数字说话。

| 模块 | 建议时长 | 说明 |
| --- | --- | --- |
| 项目深挖（第八部分） | 15 到 20 分钟 | 必问，最能区分真实经验 |
| RAG 或 Agent（按简历二选一深问） | 15 分钟 | 另一个只问 2 到 3 题 |
| 提示词与结构化输出、评估 | 10 分钟 | 几乎所有候选人都应该过 |
| 工程化与安全 | 10 分钟 | 高级必问 |
| 模型基础、微调与选型 | 按需 | 用来判断基础是否扎实 |

**追问套路**：每一题都可以用这四句往深处挖。

1. 为什么这样选？还有什么备选？
2. 你怎么验证它有效？（有没有数据、对照）
3. 出过什么问题？怎么发现的，怎么修的？
4. 规模放大 10 倍，哪里先出问题？

**判断真实经验**：让候选人讲一次踩过的坑。真做过的人会给出具体的数字、现象和排查过程；只读过文章的人会停在概念和清单上。

本文不写具体模型版本、价格和榜单，这类信息变化快，面试前自行核对。第四部分里关于 JSON 输出和重复工具调用的细节，可以配合之前那份面试题一起用。

## 一、模型基础与调用

这一部分用来判断基础是否扎实：候选人能否把模型当作一个有成本、有延迟、有不确定性的服务来使用。

### 1.1 token 为什么不等于字数？对成本和长度控制有什么影响？

- **考察点**：对计费和上下文限制的基本认知。
- **参考要点**：分词器因模型而异，中文和英文的 token 效率不同；计费按 token，输入和输出分开计价，输出通常更贵；上下文窗口是输入加输出的总和；超限会报错或被截断；估算要用对应模型的分词器。
- **追问**：你怎么在调用前预估一次请求会不会超限？
- **红旗**：用字数或字符数估算成本和长度。

### 1.2 上下文窗口越大越好吗？长上下文有什么问题？

- **考察点**：是否理解"能放进去"和"能用好"不是一回事。
- **参考要点**：成本和延迟随长度增长；信息放在中间容易被忽略，注意力被稀释；无关内容会干扰答案；应对手段：检索只放相关内容、历史摘要和裁剪、把关键指令放在开头或末尾、用提示缓存降低重复部分的成本。
- **追问**：对话历史越来越长，你怎么处理？摘要会丢什么信息？
- **红旗**：认为窗口够大就可以把所有资料都塞进去。

### 1.3 temperature 和 top\_p 各自的作用？信息抽取和工具调用场景怎么设？

- **考察点**：不是背参数，而是知道它们对输出稳定性的影响和边界。
- **参考要点**：temperature 调整概率分布的平滑程度，越低越确定；top\_p 是核采样，只在累计概率达到阈值的候选里采样；不建议同时大幅调两个；抽取、工具调用常用低温度，创意类用高一些；低温度也不能保证完全可复现。
- **追问**：你想让结果可复现，除了温度还能做什么？（记录输入输出、固定模型版本、在评估集上看分布）
- **红旗**：认为 temperature 设为 0 就一定完全可复现。

### 1.4 为什么要用流式输出？实现上要注意什么？

- **考察点**：对体验和工程复杂度的权衡。
- **参考要点**：降低首字延迟，改善感知速度；常见实现是 SSE 或分块传输；流式下结构化输出只有部分内容，解析和校验要等完整；中途掉线、取消请求、已产生的 token 仍计费；工具调用的参数也是增量到达的。
- **追问**：流式输出里出现了不安全或错误的内容，怎么拦？
- **红旗**：只知道"显示更快"，不知道对解析和错误处理的影响。

### 1.5 一个调用又慢又贵，你怎么优化？

- **考察点**：先度量再优化的习惯。
- **参考要点**：先度量（首字延迟、总时长、输入输出 token）；缩短提示词、裁剪历史；提示缓存（前缀保持稳定，易变内容放后面）；简单任务用小模型、按难度路由；独立调用并行；限制输出长度；非实时任务用批处理；相同请求做结果缓存。
- **追问**：提示缓存命中的前提是什么？你怎么设计提示词的结构来提高命中率？
- **红旗**：没有度量就下手改，或者只想到换一个更强的模型。

### 1.6 调用模型时常见的错误有哪些？分别怎么处理？

- **考察点**：对重试边界的理解。
- **参考要点**：限流（指数退避加随机抖动，遵守服务端给出的等待时间）；服务端错误和超时（有限重试，注意幂等）；参数错误和上下文超限（不重试，修正请求）；内容安全拒绝；连接和读取超时分开设置；熔断、降级、备用模型。
- **追问**：重试和超时叠在一起，用户可能等多久？你怎么算？
- **红旗**：对所有错误无限重试。

### 1.7 用自己的话讲讲：大模型是怎么一个字一个字生成文本的？

- **考察点**：是否理解自回归生成和注意力的作用，而不是背名词。
- **参考要点**：文本先切成 token，每个 token 变成向量；Transformer 由多层堆叠，每层有自注意力（每个位置根据和其他位置的相关程度汇总信息）和前馈网络；位置信息靠位置编码引入。训练目标是预测下一个 token；推理时每一步输出整个词表上的概率分布，再按 temperature、top\_p 等参数采样出一个 token，把它接到输入后面，继续预测下一个，这就是自回归。当前主流对话模型多为 decoder-only 结构。
- **结合项目**：已经生成的 token 不会被回头修改，每一步又是按概率采样，所以长输出里的小概率失误（多出一个英文双引号、少一个右括号）会直接留在结果里。这就是结构化输出需要校验和纠错重试，而不能只靠提示词的原因。
- **追问**：同一个问题问两次，为什么答案可能不同？temperature 设为 0 就能保证每次完全一致吗？（通常不保证：并行计算的浮点运算顺序、服务端的批处理等都可能带来细微差异。）
- **红旗**：只会说“注意力就是加权求和”，却说不清它和输出长度、耗时、成本、输出出错的关系。

### 1.8 KV cache、prefill 和 decode 是什么？它们和延迟、成本有什么关系？

- **考察点**：能否用推理过程解释耗时和成本，而不是只会看账单。
- **参考要点**：一次请求分两段。prefill 一次性处理全部输入，可以并行，输入越长越慢，决定首 token 延迟；decode 逐个生成输出，只能串行，输出越长总耗时越长。生成时为避免重复计算已处理 token 的注意力中间结果（key 和 value），服务端会把它们缓存下来，这就是 KV cache，它占用的显存随上下文长度和并发数增长，是服务端并发能力的重要限制。多个请求开头相同时，服务端可以复用这部分缓存（前缀缓存），所以要把稳定的内容（系统提示词、工具定义）放在最前面，把每次变化的内容放在后面；具体的缓存条件和计费以服务商文档为准。输出 token 的单价通常高于输入 token。
- **结合项目**：多轮 Agent 每一轮都把全部历史重新发送，输入逐轮变长；本项目真实运行 3 次，第 2 轮都比第 1 轮慢（3.7s→7.9s、2.1s→3.2s、1.6s→4.4s），原因是输入更长、最终回答的输出也更长。
- **追问**：一次调用首字出得很慢、总耗时也很长，怎么判断是输入太长还是输出太长？（看返回的 usage 里的 prompt\_tokens 和 completion\_tokens；流式调用时再看首 token 时间。）
- **红旗**：认为输入和输出同价同速；不知道为什么要让提示词的开头保持稳定。

### 1.9 GPT、BERT、T5 有什么区别？对话模型和 embedding 模型为什么不是同一类？

- **考察点**：对模型结构的基本分类，以及它和 RAG 选型的联系。
- **参考要点**：BERT 是 encoder-only，使用双向注意力，擅长“理解”，常用来产出文本的向量表示；GPT 是 decoder-only，使用因果掩码（每个位置只能看到它之前的内容），擅长“生成”，是当前对话模型的主流；T5 是 encoder-decoder，先编码输入再解码输出，适合翻译、摘要这类序列到序列任务。RAG 里的 embedding 模型把一段文本压成一个向量，用来做相似度检索，常见的是编码器结构，也有基于大模型改造的；它和负责生成回答的对话模型是两个模型，选型和评估都要分开做。
- **追问**：换了 embedding 模型，已经建好的向量库能直接用吗？（不能：向量空间不同，需要重新计算全部向量。）
- **红旗**：以为 embedding 和对话用的是同一个模型，或者认为换 embedding 模型只是改个配置。

## 二、提示词与结构化输出

这一部分看候选人是把提示词当手工技巧，还是当需要版本管理和评估的工程产物。

### 2.1 一个好的系统提示词包含哪些部分？怎么组织？

- **考察点**：结构化思维，而不是把需求堆成一段话。
- **参考要点**：角色和任务目标；约束和边界；输入的含义和格式；输出格式以及示例；信息不足时该怎么办（允许说不知道）；用分隔标签区分指令和数据；稳定不变的内容放前面，利于提示缓存。
- **追问**：提示词越写越长，规则之间互相矛盾怎么办？
- **红旗**：只管堆规则，不说怎么验证每条规则是否真的被遵守。

### 2.2 few-shot 示例怎么选？有什么坑？

- **考察点**：示例对模型行为的强影响。
- **参考要点**：覆盖典型和边界情况；示例里的格式必须与要求一致，模型会照抄示例（写成空数组的字段，模型就不知道元素该是什么类型）；示例太多占 token，也容易让模型过拟合示例；可以按输入动态检索示例。
- **追问**：你遇到过因为示例导致的问题吗？
- **红旗**：示例随便写，没有用评估集比较过有无示例的差异。

### 2.3 怎么让模型输出稳定的结构化结果？

- **考察点**：是否知道分层方案和每层的残留风险。
- **参考要点**：从弱到强：提示词约束 → JSON 模式 → 原生工具调用或 strict 模式 → 约束解码（json\_schema）；无论用哪种，都要用 schema 工具（Pydantic、zod）校验并处理失败；schema 尽量小而扁平；需要推理的任务，先自由推理再格式化，避免让格式约束拖累推理。
- **追问**：模型返回了非法 JSON，你的系统怎么处理？（详见第九章 9.1）
- **红旗**：认为提示词写清楚就能根治。

### 2.4 怎么降低模型的幻觉？

- **考察点**：不承诺根治，能给出多层手段。
- **参考要点**：给出依据（检索或工具）并要求引用来源；允许回答"不知道"；结果校验（规则、二次核验、交叉检查引用是否存在）；高风险场景加人工审核；明确告诉用户哪些是模型推断。
- **追问**：你怎么测量幻觉率？
- **红旗**：只靠在提示词里写"不要胡说"。

### 2.5 提示词怎么管理和迭代？

- **考察点**：是否把提示词当代码一样对待。
- **参考要点**：版本控制，和代码一起评审；模板和变量分离；每次改动用评估集回归；灰度或 A/B；请求日志里记录使用的提示词版本；禁止线上直接热改而不经评估。
- **追问**：模型版本升级后，老提示词表现变差，你怎么发现、怎么应对？
- **红旗**：提示词写在代码字符串里，没有版本，也没有回归。

### 2.6 要不要让模型"一步一步思考"？

- **考察点**：对推理成本和收益的判断。
- **参考要点**：复杂推理、多步任务通常受益；简单任务只增加延迟和成本；自带思考能力的模型，过度指导思考过程可能没有帮助；要决定思考内容是否展示给用户、是否落库；在结构化输出里放理由字段时，理由放在结论前面。
- **追问**：你怎么证明加了思考真的提高了答案质量？
- **红旗**：对所有任务一律要求逐步思考。

## 三、RAG 检索增强生成

RAG 的问题几乎都出在检索环节，所以这一部分看候选人是否能把"检索"和"生成"拆开度量，而不是笼统地说"效果不好"。

### 3.1 RAG 解决什么问题？什么时候不该用？

- **考察点**：技术选型的边界感。
- **参考要点**：适合知识会更新、数据是私有的、需要可溯源的场景；不适合：需要对全量数据做统计和聚合、资料很少可以直接放进上下文、需要改变模型的风格或行为（这类更适合微调或提示词）。
- **追问**：上下文窗口很大了，还需要 RAG 吗？
- **红旗**：把 RAG 当成任何知识问题的默认答案。

### 3.2 文档切分（chunking）怎么做？

- **考察点**：是否理解切分对检索质量的决定性影响。
- **参考要点**：按语义和结构切（标题、段落），而不是固定字数；大小要权衡：太小丢上下文，太大引入噪声且成本高；保留元数据（来源、标题层级）；表格和代码需要特殊处理；父子块（检索小块、返回大块）；用评估集调参，不凭感觉。
- **追问**：一份 PDF 里有大量表格和图片，你怎么处理？
- **红旗**：固定 500 字切一刀，没有任何验证。

### 3.3 只用向量检索够吗？你怎么提高检索质量？

- **考察点**：检索链路的工程细节。
- **参考要点**：向量检索擅长语义，关键词检索（BM25）擅长精确词、编号、专名，所以常用混合检索；召回后重排；query 改写和扩展；元数据过滤；Top-K 的取舍；embedding 模型要和语料语言匹配，更换模型需要重建索引。
- **追问**：重排增加了延迟，你怎么判断值不值？
- **红旗**：只用向量检索，也没有比较过其他方案。

### 3.4 RAG 效果不好，怎么定位问题？

- **考察点**：最能区分中级和高级的一题。
- **参考要点**：把检索和生成拆开评估。检索看召回率和命中率（正确片段是否在 Top-K 里）；生成看忠实度（是否依据片段）和答案正确性。常见失败：没检到（切分、嵌入、query 的问题）；检到了但排得靠后（重排）；检到了但模型没用或用错（提示词、上下文过长）；资料里根本没有答案（应该拒答）。
- **追问**：你怎么建立评估集？标注由谁做？怎么保持更新？
- **红旗**：只看最终答案好不好，不区分是检索还是生成的问题。

### 3.5 多轮对话里的指代（"它""这个"）怎么处理？

- **考察点**：对检索输入的处理能力。
- **参考要点**：结合历史把用户问题改写成独立的问题再检索；判断这一轮是否需要重新检索；历史要做摘要或裁剪。
- **追问**：改写本身也要调用模型，成本和延迟怎么控制？
- **红旗**：直接把用户的原话拿去检索。

### 3.6 文档会更新、会删除，不同用户可见的范围不同，怎么处理？

- **考察点**：数据治理和权限意识，高级必问。
- **参考要点**：增量更新（文档版本、内容哈希）；删除时要同步删除向量；权限作为元数据，在**检索阶段**过滤，不能等生成后再拦；审计记录。
- **追问**：用户权限变化了，已经缓存的结果怎么办？
- **红旗**：所有人的数据放在同一个索引里，没有权限过滤。

### 3.7 怎么让回答带引用，并验证引用是真的？

- **考察点**：可溯源的工程实现。
- **参考要点**：给每个片段编号，要求模型引用编号；程序检查引用的编号确实存在；必要时用二次核验判断片段是否真的支持结论；在界面上展示原文。
- **追问**：模型引用了一个存在但并不支持结论的片段，怎么发现？
- **红旗**：相信模型写出来的引用。

## 四、Agent 与工具调用

Agent 的难点不在"让模型调工具"，而在模型不可控时运行时怎么兜底。这一部分对高级候选人要深问。

### 4.1 Agent 和普通的模型调用、固定工作流有什么区别？什么时候该用 Agent？

- **考察点**：选型判断，不堆概念。
- **参考要点**：工作流的路径是预先写死的，Agent 由模型决定下一步；Agent 灵活，但不确定、成本高、难调试；能用确定流程解决的先用工作流；步骤无法预知、需要动态选工具时才用 Agent。
- **追问**：你做过的项目里，有哪一部分你最终从 Agent 改成了固定流程？为什么？
- **红旗**：任何需求都想上 Agent。

### 4.2 描述 Agent 的主循环，并说出每一处该有什么保护

- **考察点**：运行时的工程意识。
- **参考要点**：构造请求 → 模型决策 → 校验 → 执行工具 → 写入历史 → 下一轮 → 终止。保护：最大轮次、重复和无进展熔断、单次和总超时、token 或成本预算、权限检查、取消、工具失败作为结果返回给模型，而不是抛异常中断循环。
- **追问**：工具执行失败，应该抛异常还是返回给模型？什么情况下两者不同？
- **红旗**：只有 `while True` 和最大轮次。

### 4.3 function calling 和"让模型输出 JSON 再自己解析"有什么区别？

- **考察点**：协议层结构化和文本层结构化的差别。
- **参考要点**：原生工具调用由 API 层返回结构化的调用块，参数按 schema 描述，支持一轮内多个工具调用；文本 JSON 需要自己解析和容错；各服务商对 strict 和并行调用的支持不同，需要验证。细节见之前那份面试题的 A5。
- **追问**：同一轮里模型要求调用两个工具，你怎么执行？能并发吗？其中一个失败了怎么办？
- **红旗**：把两者当成一回事。

### 4.4 怎么设计一个好用的工具（名称、描述、参数、返回）？

- **考察点**：是否站在模型的角度设计接口。
- **参考要点**：描述是写给模型看的，要说明何时用、何时不用；参数少而清楚，用枚举和范围约束；返回结构化且精简，大文本要截断并提示被截断；错误信息要能让模型知道下一步怎么做；标记只读、幂等和风险等级；设置超时；输出要脱敏。
- **追问**：工具返回了一万行日志，你怎么处理？
- **红旗**：把整页日志或整个文件原样塞回给模型。

### 4.5 MCP 是什么？解决什么问题？有什么风险？

- **考察点**：对标准化协议的理解和安全意识。
- **参考要点**：把工具、资源、提示词的接入标准化，工具实现一次、多个客户端复用，常见传输方式有本地 stdio 和 HTTP。风险：不可信的服务端在工具描述里夹带恶意指令、权限过大、凭据泄露、返回内容里的注入；需要 allowlist、审批和最小权限。
- **追问**：MCP 和直接在代码里写函数工具相比，什么时候值得引入？
- **红旗**：只知道名字，说不清解决什么问题，没有安全意识。

### 4.6 Agent 的记忆怎么设计？

- **考察点**：短期和长期记忆的区分，以及写入策略。
- **参考要点**：短期即本次运行的上下文和历史；长期存在外部存储，需要时检索取回；历史要摘要压缩；事实和偏好分开存；想清楚什么值得记、怎么过期和纠错；隐私和删除。
- **追问**：记忆里存了错误的信息，怎么发现和纠正？
- **红旗**：把全部对话原样塞进上下文。

### 4.7 哪些动作需要人工确认？权限怎么设计？

- **考察点**：模型不可信前提下的权限边界。
- **参考要点**：只读、低风险的自动执行；写操作、不可逆、花钱的需要审批；支持不同权限模式（询问、自动、仅规划）；审计记录；幂等和回滚；最小权限。权限检查放在 Harness，不靠提示词。
- **追问**：审批等待期间，这次运行的状态怎么保存和恢复？
- **红旗**：靠提示词告诉模型"不要执行危险操作"。

### 4.8 多 Agent 什么时候值得用？

- **考察点**：不追潮流，能算清代价。
- **参考要点**：任务可以并行、上下文需要隔离、专长不同时值得用；代价是成本、协调、调试和一致性；单 Agent 加上好用的工具往往已经够了；子 Agent 只返回摘要，避免污染主上下文。
- **追问**：多个 Agent 给出了相互矛盾的结论，怎么处理？
- **红旗**：为了"显得高级"而拆多个 Agent。

### 4.9 模型输出了非法结构，或者重复调用同一个工具，运行时怎么处理？

- **考察点**：对可靠性机制的综合掌握。
- **参考要点**：分层防御（预防、检测、有限重试、降级、观测）；重试不重跑已执行的工具；重复调用用签名加结果指纹判断，分级熔断。完整题目见之前那份面试题的第一、二部分。
- **追问**：你的系统有哪些监控指标能发现这两个问题变多了？
- **红旗**：只靠“重试”两个字。

## 五、评估、可观测性与迭代

这一部分最能区分"做过 demo"和"做过上线"：没有评估和观测，每一次改动都是凭感觉。

### 5.1 怎么评估一个 LLM 应用的效果？

- **考察点**：是否有系统的评估思路。
- **参考要点**：先定义"好"（任务成功标准、格式、拒答、延迟、成本）；建立评估集（真实样本、边界样本、回归案例）；能用程序判断的用程序（精确匹配、字段、格式），需要判断的用 LLM-as-judge 或人工；组件级和端到端分层评估。
- **追问**：没有标准答案的开放式任务，你怎么评？
- **红旗**：手工试几个例子就上线。

### 5.2 LLM-as-judge 可靠吗？有什么坑？

- **考察点**：对自动评估局限性的认识。
- **参考要点**：存在偏好冗长回答、位置偏差、偏好自己风格的问题；用明确的评分细则、成对比较、交换顺序、用人工标注校准一致率；不能完全取代人工抽检。
- **追问**：你怎么知道 judge 的打分和人工判断是一致的？
- **红旗**：直接相信 judge 的分数，没有任何校准。

### 5.3 评估集怎么建、怎么维护？

- **考察点**：评估集工程经验。
- **参考要点**：来源包括脱敏的线上日志、人工构造、失败案例；标注标准要一致；分层覆盖；防泄漏（评估样本不能写进提示词或示例）；版本化；线上每出现一类新的失败就补进去；规模可以从几十条开始，但要有代表性。
- **追问**：评估集里的数据涉及用户隐私，怎么处理？
- **红旗**：评估集和提示词里的示例是同一批数据。

### 5.4 线上怎么做可观测？要记录什么？

- **考察点**：排查一个"答错了"的请求，需要哪些现场。
- **参考要点**：每次请求的调用链：提示词版本、模型版本、输入输出（脱敏）、每一轮的工具调用和结果、token、延迟分段、`finish_reason`、重试次数、错误类型。指标：成功率、重试率、成本、p95 延迟、工具调用次数分布、拒答率。用户反馈、采样回放、告警。
- **追问**：记录输入输出会带来隐私和存储问题，你怎么取舍？
- **红旗**：只记最终答案。

### 5.5 改了提示词或者换了模型，怎么确认没有变差？

- **考察点**：回归和发布纪律。
- **参考要点**：用评估集跑回归；灰度或 A/B；影子流量（新旧版本并行对比）；按类别拆开看，总分不变不代表每一类都没变；成本和延迟一起看；可以回滚。
- **追问**：样本量多少才够？怎么避免把随机波动当成改进？
- **红旗**：跑了几次没报错就认为没问题。

### 5.6 同一个输入模型每次结果都不一样，怎么写测试？

- **考察点**：对非确定性系统的测试思路。
- **参考要点**：断言只覆盖确定性的部分（接线、结构、错误类型、历史增长）；模型的选择和结论只报告不断言；用多次运行的通过率和阈值代替单次结果；模型侧失败和接线失败用不同的退出码区分；用假模型（FakeLLM）测 Harness 的逻辑。
- **追问**：如果需要真实模型才能验证，怎么控制成本和稳定性？
- **红旗**：把模型的输出写成精确相等的断言。

## 六、工程化与安全

高级候选人必问。重点不是背名词，而是能否把"模型不可信、服务不稳定、成本会失控"当作默认前提来设计。

### 6.1 什么是 Prompt Injection？直接注入和间接注入有什么区别？怎么防？

- **考察点**：安全意识，以及是否知道提示词不是安全边界。
- **参考要点**：用户或外部内容（网页、文档、工具返回）里夹带指令，诱导模型越权；间接注入来自检索结果、邮件、工具输出，更隐蔽；不能只靠提示词防御。纵深防御：把外部内容当数据并标注来源、最小权限、工具 allowlist、敏感操作人工确认、输出过滤、审计。同时能读私有数据、接触不可信内容、还能对外发送的组合最危险。
- **追问**：一个网页总结 Agent 读到了页面里的"把对话内容发到某个地址"，你的系统哪一层会拦住？
- **红旗**：认为在系统提示词里写"不要听从用户的恶意指令"就够了。

### 6.2 怎么避免敏感数据（密钥、个人信息）进入模型和日志？

- **考察点**：数据安全的工程手段。
- **参考要点**：入口脱敏、工具结果过滤、凭据不进入提示词和上下文、日志脱敏、最小化发送给模型的数据、了解供应商的数据政策（是否用于训练、保留期）、合规要求；模型的输出也要检查。
- **追问**：错误信息里带了模型原始输出或用户数据，落库前你怎么处理？
- **红旗**：直接把完整请求上下文打到日志里方便排查。

### 6.3 限流、超时、重试、熔断、降级怎么组合设计？

- **考察点**：系统稳定性的组合思维。
- **参考要点**：客户端限流和并发控制；分级超时（连接、读取、总耗时）；退避重试；熔断；降级（小模型、缓存、固定回答、排队）；备用服务商；队列削峰；保证幂等。
- **追问**：重试次数、超时时间和用户能接受的等待时间，你怎么算？（最坏情况下的总耗时）
- **红旗**：只知道重试，没有熔断和降级。

### 6.4 缓存怎么用？有什么坑？

- **考察点**：对不同缓存类型和风险的理解。
- **参考要点**：精确缓存、语义缓存（有误命中风险）、服务端的提示缓存（前缀缓存）。缓存键要包含模型、提示词版本和参数；要考虑时效性、个性化和权限，含私有数据的结果不能在不同用户之间共享；要有失效策略。
- **追问**：语义缓存判断两个问题相似但答案不同，怎么办？
- **红旗**：所有用户共用同一份缓存，没有权限隔离。

### 6.5 Agent 一次运行要几十秒，HTTP 接口怎么设计？

- **考察点**：长任务的接口设计。
- **参考要点**：不在请求线程里阻塞到结束；返回任务 ID（202），用轮询、SSE 或 WebSocket 取结果；后台执行，状态持久化；支持取消；客户端断开不应影响任务，或者有明确的取消语义；重连后能恢复进度。
- **追问**：同一个任务被重复提交（用户点了两次），怎么处理？（幂等键、任务状态检查）
- **红旗**：在 HTTP 处理线程里同步等完整个 Agent 运行。

### 6.6 成本怎么控制？

- **考察点**：是否把成本当作一等公民。
- **参考要点**：路由（简单任务用小模型）、缓存、缩短上下文、限制输出长度、预算和告警（每用户、每任务上限）、批处理、监控 token 分布；防止滥用（认证和配额）。
- **追问**：一个用户的任务陷入循环，用光了一天的预算，你怎么防？
- **红旗**：只在月底看账单。

### 6.7 怎么避免被单一服务商绑死？

- **考察点**：适配层设计，以及对差异的清醒认识。
- **参考要点**：模型适配层和统一的内部请求响应格式；各家在工具调用、JSON 模式、流式上的差异不能被抽象完全抹平；回退策略；固定模型版本，升级前用评估集跑回归。
- **追问**：你的适配层里哪些差异最难抹平？
- **红旗**：以为"兼容 OpenAI 接口"就意味着行为完全一样。

## 七、微调、模型选型与成本

这一部分用来判断候选人有没有"先用最便宜的方法解决"的习惯，而不是上来就想微调、换最贵的模型。

### 7.1 什么时候该微调，什么时候不该？

- **考察点**：方案选择的顺序和边界。
- **参考要点**：顺序上先提示词，再 RAG，最后才考虑微调。微调适合稳定的风格和格式、特定任务的小模型（降成本和延迟）；不适合注入经常更新的知识（用 RAG）；微调需要高质量数据、评估和持续维护，基础模型升级后可能要重做。
- **追问**：微调之后效果反而变差了，可能是什么原因？
- **红旗**：想让模型"学会公司文档"就去微调。

### 7.2 微调数据怎么准备？

- **考察点**：数据质量意识。
- **参考要点**：质量比数量重要；格式一致；覆盖边界情况；去重和去污染（不让评估集泄漏进训练集）；标注标准一致；个人信息脱敏；留出验证集；要和基线（优化后的提示词）对比。参数高效微调（如 LoRA）成本更低。
- **追问**：用大模型生成数据来训练小模型，有哪些风险？（许可条款、错误被放大、分布偏差）
- **红旗**：没有验证集，也没有和基线对比。

### 7.3 怎么做模型选型？

- **考察点**：用自己的数据说话，而不是看榜单。
- **参考要点**：用自己的评估集比较；维度包括质量、延迟、成本、上下文长度、工具调用和结构化输出能力、稳定性、数据合规、可用地区；按任务路由不同模型；保留回退选项。
- **追问**：你选定一个模型后，什么情况下会重新选？
- **红旗**：只看公开榜单排名。

### 7.4 自部署开源模型和调用 API，怎么选？

- **考察点**：对总成本和运维代价的认识。
- **参考要点**：API 的优势是快、免运维、能力领先；自部署的优势是数据不出域、高并发长期运行成本可控、可以微调；代价是 GPU、推理框架、显存和并发、运维、模型更新；要评估吞吐和延迟，量化可能带来精度损失。
- **追问**：什么规模下自部署才划算？你怎么算这笔账？
- **红旗**：只算 GPU 的钱，不算人力和运维。

## 八、系统设计与项目深挖

这一部分占面试的大头，因为前面的知识点都可以背，项目细节和设计取舍没法背。

### 项目深挖

让候选人讲一个最有代表性的项目，然后按下表的方向追问，每个方向至少追到第二层。

| 追问方向 | 示例问题 | 好回答的特征 |
| --- | --- | --- |
| 目标 | 为什么要用大模型？不用会怎样？成功的标准是什么？ | 能说出可衡量的目标和不用大模型的对照方案 |
| 架构 | 画一下数据流，你负责哪一块？ | 边界清楚，能分清个人贡献和团队成果 |
| 最大的坑 | 一次印象最深的线上问题，现象是什么，怎么定位，怎么修，怎么防止再发？ | 有具体现象、日志、数字和排查路径 |
| 数据和指标 | 效果怎么量化？上线前后对比如何？成本和延迟是多少？ | 有评估集和对照，数字自洽 |
| 取舍 | 考虑过哪些方案，为什么放弃了？ | 能说出放弃方案的真实理由 |
| 反思 | 如果重做，你会改什么？ | 能指出当时的错误判断，不只是说"更好的模型" |

**红旗**：说不清自己做了什么；全是名词没有数字；把团队成果说成个人成果；没出过任何问题；没有评估；从没考虑过成本和安全。

### 8.1 设计一个企业知识库问答系统（RAG）

- **考察点**：完整链路的设计能力。
- **参考要点**：数据接入和增量更新；切分和索引；权限过滤（检索阶段）；混合检索加重排；引用和拒答；评估和监控；成本和缓存；用户反馈闭环。
- **追问**：上线后用户说"答案不对"，你怎么排查？
- **红旗**：只说"向量库加大模型"，没有权限、评估和更新。

### 8.2 设计一个只读诊断的运维 Agent

- **考察点**：Agent 运行时、权限和可追溯性的综合设计。
- **参考要点**：工具集和权限（只读、allowlist、参数校验、超时）；知识和手册怎么加载（先目录后正文）；循环、终止和熔断；证据和结论的关联；失败和降级；人工确认的边界；审计和评估。
- **追问**：如果以后要开放"修复"动作，你要改什么？
- **红旗**：让模型直接执行任意 Shell。

### 8.3 设计一个高并发的客服对话机器人

- **考察点**：高并发、成本、安全和体验的综合取舍。
- **参考要点**：意图路由（简单问题用小模型或规则）；对话记忆和摘要；转人工的触发条件；限流、缓存和排队；流式输出；内容安全和隐私；成本监控；评估和反馈。
- **追问**：大促期间流量突然翻十倍，哪里先出问题？
- **红旗**：没有转人工和降级方案。

### 8.4 线上的大模型应用突然变差了，你怎么排查？

- **考察点**：排查思路和可观测性习惯。
- **参考要点**：先确认是不是真的变差（指标、样本）；查变更：提示词版本、模型版本、供应商、数据和索引、工具、上游输入分布；用调用链回放具体请求；用评估集复现；先回滚再定位；之后补评估和告警。
- **追问**：供应商静默更新了模型，你怎么发现？
- **红旗**：直接改提示词试试看，没有复现和回滚。

## 九、专题：模型输出可靠性与重复工具调用

这个专题只考察一件事：候选人是否把大模型的不确定性当作工程问题，用分层机制兜住，而不是靠提示词祈祷。两组题都来自本项目的真实问题：模型偶发返回非法 JSON，以及模型重复加载同一个 skill。

- **适用对象**：有 LLM 应用或 Agent 开发经验的中高级后端工程师。
- **时间**：第一、二部分各约 15 分钟，第三部分约 10 分钟，共约 40 分钟。
- **用法**：先问主问题，再按追问往深处挖。每题给出的"参考要点"不要求逐字命中，重点看思路是否分层、边界是否清楚。
- **红旗**：出现红旗里的回答，不一定要扣分，但要追问一次，确认是没想到还是真的不了解。
- **本项目对应**：纠错重试见 `docs/task/implementation.md` 的 SDD-014 14.2；重复调用观测见 14.3；熔断阈值见 PRD 待决策第 12 项。

### 9.1 第一部分：模型输出不是合法 JSON

核心判断：候选人能否说清"没法根治"的边界，并且给出分层的兜底方案。

#### A1. 让模型返回 JSON，线上偶尔解析失败，可能有哪些原因？

- **考察点**：能否把"不是 JSON"拆成不同类型，而不是笼统地说"模型不稳定"。
- **参考要点**：① 语法错（字符串内未转义的引号、缺括号、多余逗号）；② 被包在代码围栏里，或前后带了说明文字；③ 被截断（`finish_reason` 为 `length`）；④ 语法合法但字段类型不对（数组元素是对象而不是字符串）、缺字段、多字段；⑤ 模型拒答。
- **追问**：你怎么知道是哪一种？（看 `finish_reason`、原始输出的末尾、校验错误的位置和类型）
- **红旗**：只说"提示词写得不够清楚"；不知道 `finish_reason`。

#### A2. 能不能靠工程手段彻底解决？

- **考察点**：对"概率性输出"边界的认知，不盲目承诺。
- **参考要点**：不能保证 100%。约束解码（服务端按 JSON Schema 限制可生成的 token）、原生 function calling 的 strict 模式，能把语法错误压到接近 0。但仍有残留：截断、拒答、语义上的错误、服务商不支持。所以必须保留校验和兜底。
- **追问**：约束解码保证什么，不保证什么？（保证语法和 schema 形状；不保证内容正确，也救不了截断）
- **红旗**："加一句'必须返回合法 JSON'就行"；"用 json-repair 就能全部修好"。

#### A3. 如果没法根治，Harness（运行时框架）应该怎么设计？

- **考察点**：分层防御的系统思维。
- **参考要点**：五层。预防（约束解码、原生工具调用、缩短输出、简化 schema）→ 检测（校验 + 失败分类）→ 恢复（有限次的纠错重试）→ 降级（明确标记的失败或降级结果，不崩溃）→ 观测（记录重试率、失败类型、`finish_reason`）。
- **追问**：每一层各自挡住哪类问题？哪一层是最后一道防线？
- **红旗**：只有"try/except 之后重试"；没有降级和观测。

#### A4. 设计一次"纠错重试"：重试几次？重试什么？哪些错误不该重试？

- **考察点**：重试的边界和副作用意识。
- **参考要点**：次数有上限（通常 1 到 2 次）；把模型上一次的输出和具体错误的位置、类型发回去，要求重新输出；截断不要原样重试，要增大输出预算或要求更简短；拒答不重试；网络错误交给 SDK 的重试，不混在一起；已经执行过的工具调用不能因为"重写答案"而重跑；错误信息落库前要脱敏。
- **追问**：重试后又失败怎么办？重试会让延迟和成本怎么变？
- **红旗**：无限重试；重试时不带任何错误信息；重试会重复执行有副作用的工具。

#### A5. 为什么 Claude Code 这类产品不让模型在文本里手写 JSON？

- **考察点**：对"协议层结构化"和"文本层结构化"差别的理解。
- **参考要点**（典型做法，以公开可见的设计为准）：动作走模型原生的 tool_use / function calling 协议，由 API 层产出并解析结构化的调用；工具参数按 schema 校验，校验失败就把错误作为工具结果返回，模型下一轮自己改正（重试融入了 Agent 循环）；最终回答是自由文本，不要求 JSON。
- **追问**：这样做的代价是什么？（依赖服务商支持；兼容接口可能只支持部分特性）
- **红旗**：把 function calling 和"让模型输出 JSON"当成同一件事。

#### A6. 设计题：最终回答里要放大段中文，放在 JSON 字符串里经常出错，怎么改？

- **考察点**：能否从设计层面降低出错面，而不是只靠校验。
- **参考要点**：把最终回答也变成一次结构化函数调用（如 `final_answer`）；或最终回答只要 Markdown 文本，由程序按固定小节提取；限制每条长度和条数；提示词里规定字符串内不用英文双引号；把推理文字放在 JSON 外面。
- **追问**：各方案的取舍是什么？
- **红旗**：只想到"让模型更仔细"。

#### A7. 用 json-repair 之类的容错库自动修复输出，你怎么看？

- **考察点**：对"修复"和"猜测"的区分，以及对高风险场景的谨慎。
- **参考要点**：能补括号等纯语法问题，但对"游离引号"这类需要猜测的问题可能猜错；在运维、金融这类高风险场景，悄悄修复比重试更危险；若使用，应显式标记"已修复"并记录；优先重试。
- **红旗**：认为可以无条件使用，或完全不了解。

#### A8. 怎么衡量这套机制有没有效果？

- **考察点**：指标意识和样本量意识。
- **参考要点**：重试率（需要重试的请求占比）、最终失败率、失败类型分布、`finish_reason` 分布、重试带来的额外延迟和成本；重试率突升往往是提示词或模型版本变化的信号。样本量：20 次里失败 2 次，不足以判断某次提示词修改是否有效。
- **追问**：怎么设计对比实验？
- **红旗**：只看"这次跑通了"。

### 9.2 第二部分：模型重复调用同一个工具

核心判断：候选人是否明白模型的请求只是"建议"，执行、去重、熔断都是 Harness 的责任。

#### B1. Agent 为什么会重复调用同一个只读工具（比如重复加载同一个 skill）？

- **考察点**：能否从输入侧找原因，而不是把责任推给"模型不聪明"。
- **参考要点**：历史以一大段 JSON 塞在上下文里，模型没把它当成"我做过的事"；提示词里的约束被淹没；工具结果过长或格式让模型不确定自己是否拿到了内容；采样随机性；工具描述不清。
- **追问**：怎么验证是哪一个原因？（看每次请求里的历史内容，对比不同提示词的表现）
- **红旗**：认为是"模型的 bug"，没有从输入侧找原因。

#### B2. 这是模型的问题还是 Harness 的问题？

- **考察点**：对信任边界的理解。
- **参考要点**：模型发出的工具调用请求是"建议"，不是命令；执行、去重、权限、熔断都是 Harness 的职责；不能无条件信任模型的每一次请求。
- **追问**：如果工具有副作用，这个原则意味着什么？（权限检查、审批、幂等性）
- **红旗**：只靠提示词写"不要重复调用"。

#### B3. 设计一个去重短路机制

- **考察点**：去重的 key、作用域、适用范围和失效条件。
- **参考要点**：作用域是一次运行；key = 工具名 + 规范化后的参数；只对明确标记为只读幂等的工具启用（在 ToolSpec 上加标记）；命中时不执行，返回一条短结果，指向历史中已有的内容；同时计数。风险：上下文被压缩后，旧结果不在了，短结果会让模型拿不到内容，此时应改为返回原内容或重新执行；skill 内容可能变化，key 要带上版本或哈希。
- **追问**：写操作能这样做吗？（绝对不能）
- **红旗**：对所有工具一刀切；key 只用工具名，不看参数。

#### B4. 熔断怎么设计？

- **考察点**：总上限和针对重复的提前熔断的区别。
- **参考要点**：在总轮次上限（`max_rounds`）之外，针对重复或无进展的提前熔断，比如连续 2 到 3 次相同调用；熔断后强制进入最终回答（下一轮不再提供工具，或把 tool_choice 设为 none）；给上层明确的原因。
- **追问**：熔断后答案质量怎么保证？
- **红旗**：只靠 `max_rounds`，等到耗尽才报错。

#### B5. 怎么把"历史"交给模型，更不容易被忽略？

- **考察点**：对对话消息结构的理解。
- **参考要点**：把历史做成真正的对话消息：assistant 的 tool_call 加上 tool 角色的结果，而不是塞进用户消息里的一大段 JSON；模型对消息序列更敏感；可以和原生 function calling 一起改造。
- **追问**：这样改有什么代价？（改动较大，依赖服务商支持）
- **红旗**：不了解消息角色的区别。

#### B6. 重复调用出现的概率很低（比如 20 次里 0 到 1 次），还要不要做这些？

- **考察点**：工程取舍，反对过度设计。
- **参考要点**：先加计数和观测；成本最低的先做（硬上限、提示词）；去重短路这类有复杂度的，等数据说明有必要再做；但熔断是安全网，值得早做。
- **追问**：什么样的数据会让你决定做去重短路？
- **红旗**：要么"不用管"，要么"全都上"。

### 9.3 第三部分：综合与场景题

核心判断：候选人能否把前两部分的机制串成一个完整的运行时设计。

#### C1. 白板题：画出 Agent 一轮循环（调用模型 → 校验 → 执行工具 → 写历史 → 下一轮），标出你会在哪几处加防护

- **参考要点**：调用前构造请求（历史、可用工具）；调用后检查 `finish_reason`、解析与校验、失败分类与重试；执行前去重、权限检查；执行后把结果写入历史，不修改旧快照；循环层面有 `max_rounds` 和重复熔断；出口处理降级和脱敏落库；全程记录事件和指标。
- **追问**：如果工具执行超时了，应该怎么办？
- **红旗**：只画 happy path。

#### C2. 你把提示词改了，批量跑 20 次，失败从 2 次变成 0 次，能说明改动有效吗？

- **考察点**：统计和实验意识。
- **参考要点**：不能。样本太小，10% 与 3% 的差别在 20 次里看不出来；应该长期记录重试率，或扩大样本、固定条件做对照；要考虑模型输出的非确定性。
- **追问**：需要多少次才能分辨？（不要求算出精确数字，看有没有样本量和对照的概念）
- **红旗**：直接下结论。

#### C3. 重试也失败后，这次任务（比如一个故障工单）应该是什么状态？

- **考察点**：失败路径的产品和工程设计。
- **参考要点**：显式的失败状态，带失败分类的原因；保留已经取得的证据（工具结果）；不伪造答案；错误信息脱敏；允许人工重试或续跑；失败的工单不能再被当成正常工单继续处理。
- **追问**：用户此时还能继续发消息吗？应该怎么处理？
- **红旗**：吞掉异常；把半截输出当成结论。

### 9.4 本专题评分速查

中级候选人至少要能区分失败类型并说清重试边界，高级候选人还要能说出每一层防御残留的风险。

| 级别 | 第一部分（JSON） | 第二部分（重复调用） | 第三部分（综合） |
| --- | --- | --- | --- |
| 初级 | 能列出 3 种以上失败类型；知道要校验和重试 | 能说出模型会重复调用，知道要设上限 | 能画出主循环 |
| 中级 | 能区分失败类型并给出不同处理；说清重试边界；了解约束解码和 function calling | 能设计去重 key 和只读幂等标记；知道熔断 | 能指出多个防护点；有样本量意识 |
| 高级 | 能做分层设计并说出每层的残留风险；能评估原生协议的取舍；有指标体系 | 能指出历史消息化、上下文压缩与短结果的冲突；取舍有据 | 能把失败状态、脱敏、可观测性串起来 |

## 评分速查

中级候选人能讲清"做过什么、踩过什么坑"，高级候选人还要能讲清"为什么这样取舍、怎么用数字证明"。

| 维度 | 中级应达到 | 高级应达到 |
| --- | --- | --- |
| 模型基础与调用 | 理解 token、上下文、采样参数；会处理限流和超时 | 能系统地做延迟和成本优化，有度量依据 |
| 提示词与结构化输出 | 会写结构化提示词，知道要校验和重试 | 能给出分层防御方案，说出每层的残留风险；提示词有版本和回归 |
| RAG | 能搭一条完整链路；知道混合检索和重排 | 能把检索和生成拆开评估；有权限、更新和引用验证的设计 |
| Agent 与工具 | 理解主循环和 function calling；工具描述写得清楚 | 能设计熔断、权限、记忆和历史表示；知道 MCP 的安全风险 |
| 评估与可观测 | 知道要有评估集，记录关键日志 | 能上线回归、灰度、校准 judge；有指标体系和样本量意识 |
| 工程化与安全 | 知道 Prompt Injection 和数据脱敏 | 能做纵深防御，把异步任务、成本预算和限流降级组合起来 |
| 微调与选型 | 知道先提示词、再 RAG、最后微调 | 用自己的评估集选型；能算清自部署的总成本 |
| 项目深挖 | 能讲清个人贡献和一个具体的坑 | 有数字、对照、取舍和反思，能主动指出自己方案的局限 |

**通过线的参考**：中级在其中 6 个维度达到中级水平且项目深挖过关；高级在评估、工程化与安全、项目深挖三项都达到高级水平，其余维度不低于中级。这只是起点，请按岗位调整。
